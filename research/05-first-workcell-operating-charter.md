# 产品建设工作单元运行约定

**工作单元：** 用户 + AI，共同建设面向其他团队的智能组织产品。首个目标客户暂定小型客服 / IT 支持团队；这是产品切入口假设，不等于客户已确认。

**使命：** 把“建成一个智能组织”的目标做成其他团队可以使用的产品；同时让产品建设过程有清楚的任务、责任、审查和结果反馈。产品团队的内部协作与客户组织的智能化是两件要分别验证的事。

## 人与 AI 的分工

| 角色 | 负责事项 | 决策边界 |
|---|---|---|
| 用户（组织负责人） | 定方向和优先级，提供真实工作情境，审阅重要结论，决定是否发布或改变真实流程 | 保留业务目标、真实数据使用、对外发布和高影响行动的最终决定权 |
| AI 研究角色 | 查找依据，区分来源事实、推断和未知信息 | 不把模拟样本、公开规则或模型推断包装成组织制度 |
| AI 产品角色 | 把目标拆成任务、验收条件和人机交接 | 不擅自改变项目目标或扩大自动权限 |
| AI 实现角色 | 修改代码和文档，记录实际变更 | 只在已授权范围内写入；用户未要求测试或验证时，不添加或运行自动化测试 |
| AI 复核角色 | 对照验收条件检查结果，指出遗漏和风险 | 复核不能取代用户对业务正确性的判断 |

这些 AI 角色是同一助手的工作方式，不表示当前已有多个独立 Agent 或真实员工团队。

## 每项任务的最小记录

1. **目标：** 这次工作要改变什么实际结果？
2. **输入：** 使用了哪些来源、数据和假设？
3. **负责人：** 谁负责完成，谁对结果作最终判断？
4. **边界：** 哪些数据、系统和动作不能碰？哪些操作必须由人确认？
5. **验收：** 什么证据能证明任务完成？
6. **结果：** 交付是否被接受、修改、退回或产生后续问题？
7. **学习：** 哪条经验值得共享，哪些内容只适用于这次任务？

## 工作闭环

```text
用户提出任务
  → 共同澄清目标和验收标准
  → AI 研究 / 规划 / 实现
  → 人工复核并决定采纳、修改或退回
  → 在实际使用中观察结果
  → 记录问题、更新项目知识或流程
  → 在下一项相似任务中检验是否减少返工或改善质量
```

知识只有在后续任务中被正确使用，并对结果有可观察的帮助，才算产生了组织价值。单次好回答、被引用次数、生成量或工具调用量都不足以证明组织学会了。

## 首期观察指标

- **交付周期：** 从任务明确到用户接受交付用了多久。
- **返工：** 用户需要几轮重要修改；退回原因是什么。
- **交付后问题：** 后续是否发现缺陷、错误来源或遗漏的边界。
- **经验迁移：** 后续相似任务是否正确复用了已验证做法。

当前没有可靠的历史基线，不对旧任务补造数据。先从下一批实际项目任务开始记录，再决定是否需要量化目标。

## 当前边界

- 现有客服工单、GitHub PAT 知识卡和 4186 数据属于模拟练习，不代表用户所在组织的真实业务。
- 当前项目建设仍是一个人和一个 AI 助手的工作单元，不构成多成员客户组织实验。
- K5 仍是待审核的模拟知识；它不是本项目组织成效的验收指标。
- 要扩展到真实团队，先确认组织范围、任务类型、参与者、数据授权和结果指标。
