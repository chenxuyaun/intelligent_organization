## 问题

GitHub Enterprise Cloud 企业管理员设置 classic PAT 最长期限 30 天；下属组织设置 90 天。成员创建了一张 60 天的 classic PAT，用它访问个人仓库成功，访问该组织的私有仓库/API 被拒。请说明哪一个期限适用、被拒是否证明 token 已撤销，并列出不泄露凭证的核查步骤。

## 答复 A

判断：企业级 30 天上限优先于组织级 90 天配置，组织不能把 classic PAT 最大有效期设到超过企业上限。因此，创建时选择 60 天的 classic PAT 对 30 天上限不合规，可能仍可访问个人仓库，但会被阻止访问该组织及其私有仓库/API。组织 API 被拒并不证明 token 已被撤销或停用；设置策略本身不会撤销或停用 token，只是阻止其访问该组织。企业级策略下，期限会在使用 token 或尝试 SSO 授权时检查，错误通常会提示调整期限或生成符合要求的新 token；具体恢复步骤应依管理员指引，不要断言只有重新生成一种方式。请勿在工单中粘贴 token 明文。

**待核实：**未提供真实企业/组织策略状态，无法核实 30 天与 90 天配置是否实际生效，也无法确认目标组织是否受企业策略管理；未提供组织 API 被拒的错误文本，无法排除期限策略之外的其他权限或 SSO 原因；公开指引未规定唯一恢复步骤。

## 答复 B

按 GitHub 公开的 classic PAT 规则，若该组织确由该企业拥有且企业级最长期限策略生效，企业级 30 天是上限，组织级 90 天不能把上限放宽到超过企业级；因此这张 60 天的 token 对该企业下属组织资源会因超过企业上限而被拒，个人仓库不受同一组织策略约束，所以仍可能访问成功。组织请求被拒不等于 token 已被撤销：它可能仍是有效凭证，只是不能用于该组织资源；个人仓库访问成功也说明它至少没有被全局撤销。请仅以只读方式核对策略归属和 token 当前状态，不要通过撤销、轮换、重新生成或使用该凭证调用 API 来验证。

**待核实：**未找到可核实的制度依据，需人工核实现行制度（企业/组织 classic PAT 期限策略及适用主体）；该组织是否受企业策略覆盖尚未确认；被拒的具体错误类型/状态未知，不能仅凭“组织请求被拒”排除 SSO、成员权限、仓库权限等其他原因。
