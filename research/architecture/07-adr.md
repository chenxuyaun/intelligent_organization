## ADR-001：部署与数据隔离——每客户独立部署 + 独立数据库（追认现状）

**背景：** 产品原则 4 要求"单团队安全试点"；现有 compose.yaml 已是每团队一个容器+一个数据卷+独立 env。需要决定未来是否走向共享多租户。

**备选方案：**
- A. 共享数据库多租户（行级 tenant_id）：资源效率高；跨租户泄漏风险集中在一个查询 bug；备份/删除/合规按客户切分困难；信任模型复杂化。
- B. 每客户独立部署+独立库（现状）：物理隔离天然成立（备份、删除、迁移、审计都按实例）；代价是 N 份运维。
- C. Schema 级隔离（同库不同 schema）：介于两者，SQLite 不支持，需换数据库。

**决策：** B，即保持每客户独立部署 + 独立 SQLite。单宿主多实例通过运维清单管理（⑥§7），不做共享租户。

**代价：** 每增加一个团队 = 一份镜像运行成本与备份职责；升级需逐实例执行（脚本化摊薄）；集中报表（如果未来要多团队汇总观察）需独立只读聚合层。

**风险：** 实例配置漂移（某团队忘开 product 模式/误开 demo）→ drift-check 脚本缓解；实例数量增长后人工运维不可持续。

**重评条件：** 目标团队数 >20 且运维成为瓶颈时，评估"集中控制面 + 分布式数据面"（控制面只管配置/监控，不碰业务数据）；或客户明确要求 SaaS 形态时（那将是产品级新决策，不是本架构的延续）。

## ADR-002：模块边界——单进程内五域逻辑分层，不拆服务（追认现状+组织化）

**背景：** ①审计显示 24 个模块职责清晰但无明文边界；②提出了五域映射（任务/建议/记忆/治理/平台）。

**备选方案：**
- A. 现状（模块自由互调，无域约束）。
- B. 五域逻辑分层 + 单向依赖规则（HTTP→API→域→store/llm；域间经公开函数）。
- C. 直接拆微服务（任务服务/建议服务/记忆服务…）。

**决策：** B。理由：试点规模下 C 的收益（独立伸缩/部署）不存在，成本（网络边界、事务边界、运维）立即可见；B 用约 20 行注释级约定 + 依赖审查即可获得 80% 的可演进性。

**代价：** 需要纪律维持（域间不直查他域表）；lint/审查无自动强制（可选：脚本 grep 检查跨域 import，列入 P2）。

**风险：** 未来域内代码膨胀后拆分仍需真实重构——接受，因为接缝（searchMemory 签名、llm 单出口、addEvent 单入口）已把最难拆的部分预先隔离。

**重评条件：** 任一域需要独立伸缩（如检索负载独立增长）、或出现第二个写进程时，按 ADR-006 的拆分条件启动。

## ADR-003：独立任务队列 or 模型执行器？——暂不引入，同请求内完成（新决策）

**背景：** 模型调用目前与 HTTP 请求同生命周期（①R6）。是否引入后台队列/独立模型 worker？

**备选方案：**
- A. 引入持久化队列（SQLite 表作队列 + 轮询 worker）：可后台批量、可重试、进程崩溃可续；代价：状态可见性复杂化（"运行中"状态机、超时清理、UI 轮询）、双写一致性（队列与 runs）、代码量 +数百行。
- B. 独立 worker 进程：隔离崩溃域；代价：跨进程共享 SQLite 写锁、部署复杂度翻倍。
- C. 维持同请求内执行 + 轻量并发上限（现状 + ⑤§4 的并发计数）。

**决策：** C。负载模型（⑤§1.2）显示峰值并发 ≤4，单线程天然排队已够；用户等待模型结果本身是产品行为（成员要立刻看建议），后台化不改善体验。

**代价：** 模型慢 = 请求挂起（45s 上限）；服务重启丢进行中请求（无重试，用户手动重跑）；无法批量夜间预跑。

**风险：** 若产品假设错了（比如团队希望"提交后去忙别的"），需要补 A 路线。

**重评条件（满足其一即重开）：** ① 并发运行持续 >10；② 出现"批量导入历史工单预跑建议"需求；③ 单请求内模型+落库超过 SQLite 锁等待上限（实测出现）。届时首选 A（SQLite 表队列 + 同进程 worker），仍不拆进程。

## ADR-004：完整事件溯源 vs 普通表+审计事件——普通表+审计事件（追认现状）

**背景：** events 表是追加式审计，不是事件溯源（①§1.2）。是否升级为事件溯源（以事件为唯一事实源，状态为投影）？

**备选方案：**
- A. 完整事件溯源：时间旅行、天然审计；代价：所有读路径改投影、迁移复杂度大增、SQLite 下事务模型变复杂、开发心智负担。
- B. 普通表 + 追加审计事件（现状）：状态查询简单直接；事件满足审计与派生统计（team-learning 全靠它）；代价：事件与表状态可能不一致（同一事务内写入缓解）、无法从事件重建全部状态（payload 不含全文）。
- C. 混合（关键实体溯源，其余普通表）：边界模糊，两套模式并存成本最高。

**决策：** B（现状）。产品需要的是**可追溯审计**（谁在何时以什么授权做了什么）而非**可重放建模**；payload 白名单（④§3.2）保证审计够用且不含敏感正文。

**代价：** 不能"回到过去"看历史状态全貌（如某天的完整工单快照需按事件+主表联合推断）；跨表一致性靠同事务写入纪律。

**风险：** 若未来产品核心变成"流程编排/自动化"，事件溯源收益上升。

**重评条件：** 出现①需要重放/回放流程的需求；②派生统计开始反写事实表（当前全部只读）；③审计需要超出 payload 的更细粒度历史（此时优先考虑扩 payload 白名单，而非整体溯源）。

## ADR-005：本地快速模型 ↔ 主模型协作——主模型优先，本地模型暂缓（新决策）

**背景：** 原则 5 要求分层快速响应。research 文档提到本地小模型/JEV 用于低风险分类。现状无本地模型（①R2）。

**备选方案：**
- A. 现在就接本地小模型（如环回 Ollama）：数据不出内网（分类场景）；代价：新增运维对象、新增失败模式（①R3 要求降级预案）、质量未经标注数据验证、试点团队无 GPU 保障。
- B. 规则快路径（确定性逻辑/缓存）+ 主模型两级：零新依赖、零外发、可解释。
- C. 影子方式先评估：本地模型旁路跑分类，与人工最终类别对比，攒准确率数据后再决定启用。

**决策：** 先 B 后（可选）C，A 暂缓。快速响应收益先从"重复工单命中 + 应用段 <400ms"拿（⑤§1）；本地模型在 ⑤§5 的拒绝条件全部有解、且 C 方式攒到准确率证据后再评估。

**代价：** 分类/路由仍走主模型路径（延迟/费用全额）；"本地模型降级"机制暂缺（无本地模型即无此故障模式，反而是现状优点）。

**风险：** 若模型成本/延迟实测超预期，可能被迫提前引入本地路径——届时按 ⑤§5 的适配/拒绝条件实施，架构无需改动（llm.js 已支持环回 HTTP）。

**重评条件：** ① 试点延迟四元组报表显示分类类请求占比高且延迟痛感强；② 出现"数据绝不能出内网"的新客户约束；③ 本地模型在合成标注集上分类准确率达标（阈值待定）。

## ADR-006：何时拆分服务 / 引入多租户——显式触发条件清单（新决策）

**背景：** 原则 8 要求"不过早引入分布式"。需要把"什么时候才拆"写成可检验条件，防止两种失败：过早拆（复杂度爆炸）与过晚拆（性能/合规事故）。

**决策：** 全部维持单体+独立实例，直到以下任一条件**实测成立**（不是预测）：

| 触发器 | 阈值（暂定，实测后修订） | 拆什么 |
|---|---|---|
| T1 并发压力 | 并发模型调用持续 >10 或非模型 API p95 > 500ms | 模型执行器独立进程（ADR-003 的 A 路线先行） |
| T2 检索规模 | 语料 >10k 卡且检索 p95 > 500ms | 检索层换向量索引（独立服务或嵌入式，先嵌入式） |
| T3 数据规模 | SQLite 单库 >10GB 或备份窗口 >15min | 数据层评估（分库归档，仍不共享租户） |
| T4 产品形态 | 客户要求跨团队汇总/共享知识 | 这是产品级变更：新 ADR 决定聚合层形态，业务库仍隔离 |
| T5 团队规模 | 单实例团队 >50 成员或日工单 >1000 | 应用无状态部分横向扩容（SQLite→ Postgres 迁移评估） |

**代价：** 触发器需要监控支撑（⑤§6 的四元组报表是前置）；清单可能漏掉新维度（每季度随试点数据复核）。

**风险：** 无。

**重评条件：** 本清单本身每季度复审一次；任何触发器命中即开新 ADR，不在本文档内打补丁。

## ADR-007：检索技术——进程内 BM25 起步，向量检索沿接缝替换（追认现状+演进预案）

**背景：** retrieval.js 头注释已记录"不用 FTS5：CJK 分词、语料小、可解释性"。检索质量直接决定"后续任务寻找相关经验"（产品能力 6）。

**备选方案：**
- A. SQLite FTS5：零额外组件；CJK 需 trigram 或外部分词，中文召回差。
- B. 进程内 BM25（现状）：可解释（ref/score 可展示）、零依赖、fail-closed 过滤逻辑同进程；代价：全量扫描 O(N)、无语义召回（同义不同词查不到）。
- C. 向量检索（外部嵌入 API 或本地嵌入模型）：语义召回强；代价：语料需嵌入（费用/延迟/本地化决策）、向量库组件、**嵌入服务也是数据出口**（若远程）——触发与模型同级的授权闸门问题。

**决策：** 现状 B；演进按 ADR-006 T2 触发，届时优先**本地嵌入 + SQLite 存向量 + 内存近似检索**（保持单文件部署），`searchMemory(query, corpus)` 签名不变。远程嵌入 API 因引入第二个数据出口，必须先过与 pilotRunGate 同级的授权设计（新 ADR）。

**代价：** 语义召回缺口短期内用"提示词引导模型改写查询"缓解（成本一次调用，可选）；混合过滤逻辑（scope/自排除/过期）必须在新检索层原样保留——已固化为 fail-closed 语义测试（列入 smoke 扩展）。

**风险：** 检索质量差导致"经验存了但找不回"，产品能力 6 空转——观察批次已有 citation 数据可监控；helpful 跟踪（④§6）上线后能直接度量"找回且有用"。

**重评条件：** helpful 率数据显示"命中但无用"占比高（检索不相关）或成员反馈找不到已知存在的经验（召回缺口）→ 提前启动 C 评估，不等 T2 阈值。

**实测补充（2026-11-20，`scripts/perf-baseline.js` 合成语料 5 轮中位）：** BM25 无预索引检索包络——1k 卡 p50=133ms（SLO <500ms 达标）、5k 卡 p50≈28s、10k 卡 p50≈110s。**>1k 卡即超可用阈值**（单进程事件循环被阻塞数秒级）。这把本 ADR 的重评从"语料量级预测"变为"已有实测依据"：语料接近 1k 卡时必须先做预索引（tokenize/tf 持久化）或直接启动 C 路线评估。试点规模（<100 卡）余量充足，不触发。

## ADR-008：领域模型——通用 WorkItem 为根概念，客服工单降为首个场景适配（新决策，2026-11-20 用户修正触发）

**背景：** 用户明确：产品核心面向通用组织协作；客服/IT 支持是研究中暂定的验证场景，不是领域模型。现状代码中 `tickets` 是全系统根概念（状态机、API、UI、检索术语全部客服化）。需要决定：维持 ticket 根模型，还是重构为通用任务模型，以及如何演进。

**备选方案：**
- A. 维持 ticket 为根模型，产品定位收窄为"客服工单工具"：实现最省，但与用户目标（通用组织协作）冲突，第二种场景出现时被迫推翻重来。
- B. 一次性重构：新建 work_items 统一表 + 迁移全部数据 + 改全部 API/前端：模型最干净，但破坏现有功能、迁移风险大，且在只有一种类型实例时抽象风险最高（"为通用化而抽象得无法理解"）。
- C. 渐进演进：概念重命名（代码层 WorkItem）→ 类型层（work_item_types 描述对象 + tickets 加列）→ 通用读模型路由 → 第二类型接入验证 → （远期、条件触发）表归并。每步独立可交付、可回退。

**决策：** C。核心依据：现状 tickets 的**结构**已经是通用工作项（标题/描述/负责人/状态/结果/交接），客服性只存在于命名、词表与术语层——这些恰好是可以低成本类型化的部分。核心机制（权限阶梯、审核权威、交接验证、scope/有效期、审计、采用/有效跟踪）只实现一次，全部类型共享；适配层只声明词表/表单/术语，不能改变核心语义。

**代价：** 过渡期"概念名（WorkItem）与存储名（tickets）不一致"，需要文档与代码注释持续对齐（E3 的读模型路由缓解）；类型描述对象是新的小维护面（每类型一份词表 JSON）；E5 前数据库表名保持历史命名。

**风险：** 抽象 leak（某适配需求要求改变核心机制）→ 硬约束护栏：适配层无权改核心机制，需求冲突时开新 ADR；第二种类型始终不来 → E4 不启动，系统停留在"单类型 + 已备好接缝"，无额外成本；过早通用化（没等第二个实例就重构表）→ E5 显式设置触发条件防止。

**重评条件：** ① 第二种任务类型（如"新产品试点准备"）接入后，若发现类型描述对象表达不了其需求（需要改核心表/机制），重开本 ADR；② 类型数 ≥3 且跨类型查询成为高频路径时，评估 E5 表归并；③ 客户明确需要自定义类型/字段时，升级为"类型配置化"新 ADR（仍不做可视化搭建器，v1 边界不变）。

## ADR-009：工具连接器——类型化注册表，副作用必经人工审批（新决策，⑨ 执行闭环）

**背景：** 产品核心要从"建议域"扩展到"执行域"（自然语言目标 → 周报/邮件等实际工作，总纲 §四/§五）。现有系统没有任何外部工具集成；模型能力被限制在三个只读/产草稿工具。执行外部副作用（发邮件、发布、修改外部记录）引入新的信任问题：外部凭证、审批后内容替换、结果不确定。

**备选方案：**
- A. 直接给模型 API 调用能力（function calling 全开放）——被否：违反权限阶梯，模型自由文本不能成为执行入口。
- B. 一次性引入第三方工作流/自动化平台（n8n/Zapier 类）——被否：引入外部运行时与凭证托管，超出单客户独立部署边界（ADR-001），且审批链不可控。
- C. **类型化连接器注册表（代码内常量起步）+ external_actions 审批表 + payload_hash 审批绑定**——采纳：与现有机制同构（授权快照≈model_authorized_*，幂等≈运行去重，审批≈审核权威），无新基础设施。

**决策：** 采用 C。连接器描述对象含 owner/scope/side_effect/幂等类型/param_schema（⑨§4.1）；side_effect=true 的操作一律 prepared→人工审批（绑定 payload_hash）→执行前重验；结果四态含 outcome_uncertain（禁止自动重试，人工核实闭环）；凭证只存引用（secrets 文件），不进事件/提示词/日志；外部内容只作数据（提示注入防线 ⑨§4.5）。v1 不选择任何具体邮件/文档/日历提供商——连接器接口先行，提供商选择列为用户决策点（README D-7）。

**代价：** 副作用操作多一次人工审批（产品定位要求，非缺陷）；连接器层是新模块（约一域，依赖方向入核心域）；external_actions 新表（④§11.2，P7 前实施）。

**风险：** 连接器错误类别覆盖不全 → error_classes 枚举 + 未知类别按 ambiguous（走 outcome_uncertain）处理；审批人误批准 → payload_hash 绑定所见内容 + 执行前重验 + 审计留痕；个人连接器越权读共享数据 → scope 校验 + 内容不进共享语料。

**重评条件：** ① 出现高频批量副作用需求（人工审批成为吞吐瓶颈）→ 评估"批量预授权"新 ADR（白名单收件人/模板锁定）；② 连接器数 ≥4 且类型相似 → 评估抽象连接器基类；③ 出现 provider 原生审批/回执能力 → 评估双向状态同步。
