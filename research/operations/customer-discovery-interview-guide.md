# 客服 / IT 支持团队访谈指南

**用途：** 判断小型客服 / IT 支持团队是否真的有值得解决的重复问题、交接和经验复用困难。用于产品方向探索，不是销售话术，也不能单独证明市场需求。

**状态：** 访谈前准备；尚未访谈真实团队。  
**编制日期：** 2026-11-20。  
**建议时长：** 25 分钟。  
**适用对象：** 一线处理成员、团队负责人或负责流程 / 知识库的人。尽量先分别访谈，避免负责人替一线成员回答。

可访谈小型 MSP / 外包 IT、企业内部 IT 或客服团队；初轮若能接触到，尽量覆盖两种团队类型，看看问题是否集中在某个场景。少量访谈只用于发现差异，不追求统计代表性。访谈可以线上进行，不要求受访者或研究者到场；异地演示通过屏幕共享完成，本机 `127.0.0.1` 地址不能直接发给远程受访者。

## 开始时可以这样说

> 我在了解客服 / IT 支持团队怎样处理重复问题，以及交接和经验复用哪里费力。目前还在研究阶段，不是来推销产品。我想听一个最近真实发生的例子。请不要提供客户姓名、账号、密码、工单原文或其他敏感内容；用概括说法就可以。你不方便回答的部分可以跳过。我可以记匿名笔记吗？

如果对方不愿意匿名记录，就只听，不做记录。未经明确许可，不录音、不截图、不索取工单导出或内部制度。

## 快速版：第一次 15 分钟谈话

如果对方只方便聊 15 分钟，按这个顺序走；先听真实经历，最后再决定要不要展示预览。

| 时间 | 做什么 | 可以直接问 |
|---|---|---|
| 0–2 分钟 | 说明研究目的、敏感信息边界，确认能否匿名记笔记 | “我不需要工单原文或客户信息，只想听一个概括后的例子。可以匿名记几条吗？” |
| 2–8 分钟 | 还原最近一次交接或重复排查 | “最近一次类似问题是什么？前一个人做了什么？接手的人还得补问什么？最后怎么结束？” |
| 8–11 分钟 | 了解重复频率、影响和已有办法 | “上个月大概发生几次？这个数字来自系统、估算还是印象？你们现在用什么工具或流程？最近一次哪里仍不顺？” |
| 11–13 分钟 | 了解试用决策与数据限制 | “谁会日常处理、谁要批准新流程？哪些信息不能放进工具或发给模型？” |
| 13–15 分钟 | 仅在对方愿意时展示虚构预览，收集反例 | “它和你们现在的交接哪里相像、哪里不对？哪些信息没用或会增加重复录入？” |

不要先介绍“智能组织”或 AI 能力；不要问“你会不会用 / 买”。对方愿意看演示不等于购买或试用承诺。展示时只用虚构页面，不录入真实工单；如果对方不愿意看，就直接结束，不追问理由。

## 90 秒虚构演示顺序

先听对方讲完真实经历，再询问是否愿意看演示。演示只用本机虚构页面，可通过面对面展示或屏幕共享；`127.0.0.1:4195` 是本机地址，不能当作远程受访者可直接打开的链接。

1. 打开 `http://127.0.0.1:4195/#/memory`，指给对方看 K1 经验卡及其来源工单 #901，说明这是虚构案例，只有模拟审核后才进入模拟记忆。
2. 打开 `http://127.0.0.1:4195/#/t/902`，说明另一张相似的虚构工单引用了 K1；成员修改并采纳了建议，再把处理进展、人工确认内容和还未执行的步骤交给同事。
3. 不解释功能清单，只问：“这和你们最近一次类似问题的处理过程，哪里不一样？”以及“如果另一位同事接手，还缺什么信息？”
4. 记录对方指出的具体不符、遗漏或额外录入；不要把“看起来不错”记为需求、试用承诺或效果证据。

页面是只读内存演示，不连接真实数据库或模型；#902 仍为处理中，没有虚构最终解决结果。

## 活动现场：两分钟判断是否适合后续访谈

活动参会者不一定是首批目标用户。先了解岗位和实际经历，不要一上来介绍产品：

1. “你现在是亲自接 IT 支持 / 运维请求，还是主要做平台、咨询或产品？”
2. “最近一次同事交接时，接手的人最需要补问什么？后来怎样确认问题解决？”
3. 如果对方能讲出亲自处理或管理的近期案例，再邀请做 15 分钟访谈；只记匿名概括，不索取工单、公司资料或敏感信息。

如果对方主要做售前、产品或咨询，可以记作行业观点，但不要把这类谈话计作目标用户访谈。

## 访谈顺序

先问发生过什么，再问现有做法和影响。不要先介绍 AI、产品方案或“智能组织”，避免让对方迎合你的设想。

### 1. 了解最近一件具体的任务（5 分钟）

- 请讲讲最近一次比较典型的支持问题：它是什么类型，最后怎样处理？
- 从收到问题到确认解决，经过了哪些步骤？谁参与了？
- 哪一步最花时间，或最容易卡住？上一次是什么时候发生的？
- 如果当时你不在，另一位同事能否接着处理？他还需要知道什么？

追问时只要可匿名的概括；不要要求对方展示工单、客户资料或系统画面。

### 2. 看看这是不是反复出现的问题（4 分钟）

- 过去一个月大约遇到过几次类似问题？这个数字是系统统计、估算，还是印象？
- 哪些情况其实看起来相似、处理方法却不同？
- 最近有没有一次因为信息缺失、交接或重复排查而返工、升级或重新联系？发生了什么？

记录数字的来源；估计值不要写成系统事实。

### 3. 了解团队现在怎样协作和留经验（5 分钟）

- 同事遇到类似问题时，通常去哪里找已有处理办法？
- 处理经验通常由谁记录、审核和更新？哪些内容会过期或容易误用？
- 转交任务时，接手人最常需要补问什么？
- 你们现在用哪些工单系统、知识库或聊天工具？最近一次处理时，哪些步骤在这些工具里完成，哪些要到别处找信息或重复录入？
- 现有工具能不能找历史案例、推荐知识、帮助交接或记录结果？你们实际用过哪些？最近一次使用时发生了什么？
- 有什么现成流程、知识库或工具已经解决了这件事？哪些地方仍不够？

### 4. 了解实际影响和判断方式（5 分钟）

- 这个问题给团队或服务对象造成过什么具体影响？最近一次的影响是什么？
- 团队目前会看哪些记录判断问题是否解决、有没有返工？
- 如果只能改善一件事，你会选什么？为什么？
- 哪类错误或场景必须交给有权限的人判断？

优先记可核实的结果，例如多一次转接或重复询问；不要把“大家觉得麻烦”直接换算成成本或效率提升。

### 5. 了解谁能决定试用、哪些边界必须先满足（4 分钟）

- 若团队要试一种新流程，谁需要同意？谁会日常使用？
- 如果多用一套独立工具，会增加哪些录入、权限或交接工作？什么条件下你会倾向于替换现有系统、与它并用，或完全不加新工具？
- 哪些数据绝不能放进新工具？数据通常允许存在哪里、由谁查看？
- 团队使用外部 AI 服务前，需要经过什么审批？
- 之前试过哪些办法？为什么继续使用或停掉？

这里只收集决策流程和数据类别，不索取凭证、内部政策原文或个人信息。

### 6. 收尾（2 分钟）

- 我刚才理解的主要困难是……，哪里说得不准确？
- 是否还有一个近期例子能帮助理解？只需匿名概括。
- 如果后面做出一个不接真实数据的演示，是否愿意再看一次？不方便也没关系。

不要把“愿意看演示”记成购买意愿、试用承诺或需求验证。

## 匿名记录表

| 项目 | 记录 |
|---|---|
| 日期 / 访谈编号 | 不记姓名；例如 I-01 |
| 团队类型 | MSP / 外包 IT / 企业内部 IT / 客服 / 其他 |
| 受访角色 | 一线处理 / 负责人 / 流程或知识维护 / 其他 |
| 最近问题类型 | 只记类别，不抄原文 |
| 最近一个具体例子 | 发生了什么、谁接手、怎样结束 |
| 频率及数字来源 | 统计 / 估算 / 印象 |
| 卡点与返工 | 对方描述的具体事件 |
| 当前解决办法 | 工具、流程、人员协作 |
| 影响证据 | 对方明确给出的结果；没有就写“未提供” |
| 决策人与数据边界 | 角色或流程，不记敏感身份信息 |
| 直接观察到的事实 | 与受访者解释分开写 |
| 尚未确认的假设 | 例如“交接摘要可能减少重复询问” |
| 原话（可选） | 仅在获准匿名记录时，且不含敏感内容 |
| 后续动作 | 仅记对方明确同意的事项 |

访谈笔记只用于这项研究；未获授权不上传到模型、产品工作区或共享知识库。

## 访谈后怎么判断

每次访谈后，分别标记：

- **具体经历：** 对方能否描述最近实际发生的一次任务，而非只谈理想情况。
- **重复程度：** 是否有可信的频率信息，或只能凭印象。
- **现有替代办法：** 团队已经怎样解决，仍有什么未解决部分。
- **可观察影响：** 是否有返工、等待、升级或结果质量的具体证据。
- **组织条件：** 谁使用、谁批准、数据和外部模型有哪些边界。
- **下一步意愿：** 受访者明确同意了什么；不要推断购买或上线承诺。

访谈只能帮助修正问题和产品假设。少量访谈不能证明市场规模、客户愿付费、产品能改善业务，也不能证明智能组织能力已经形成。只有不同角色反复讲出相近的具体问题，才值得进入受控试用设计；若问题、频率或现有替代办法差异很大，就先调整目标团队或任务类型，不急着加功能。

## 询问社区管理员的短讯

如果通过社区招募，先问管理员是否允许发布，不要直接把招募消息群发：

> 你好，我在研究一款面向小型客服 / IT 支持团队的早期产品，想邀请一线处理成员或团队负责人做一次 15 分钟访谈，只了解重复问题和任务交接的实际做法，不收集工单、公司内部资料或敏感信息，也不是销售推广。请问贵社区是否允许发布这样的访谈招募？如果有更合适的活动或渠道，也请指点；不合适的话我就不发布。
